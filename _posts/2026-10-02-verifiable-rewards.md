## “能自动判分”并不等于“奖励天然正确”

RLVR 通常指利用可验证奖励进行强化学习，例如数学题最终答案是否正确，程序是否通过测试，棋局是否获胜。相较于让奖励模型预测人类偏好，验证规则可以更明确，也容易自动重复运行。

但验证器始终只检查它被写进去的条件。程序通过十个测试，不等于所有输入都正确；最终数字正确，不等于过程每一步成立；格式符合 JSON，也不等于内容有用。奖励定义越窄，越要清楚模型究竟在优化什么。

[DeepSeek-R1 的早期报告](https://arxiv.org/abs/2501.12948v1)使用了面向可验证任务的规则奖励等设计。该报告提供的是特定训练流程的证据，不能据此推导“任何模型只要加正确性奖励就会获得通用推理能力”。

## 一份奖励合同应该写到多细

设题目要求输出整数答案。奖励合同至少需要规定：是否允许解释文本；最终答案的标记是什么；是否允许多个候选；空白、正负号、前导零和 Unicode 数字怎样处理；超过长度上限怎么办；解析失败是零分、单独状态还是重试。

这些细节直接影响可优化行为。如果验证器只检查“输出中包含正确数字”，模型输出从 0 到 100 的所有整数就有机会得分。如果抽取最后一个数字，答案之后附带的编号可能改变分数。验证器不是训练前随手写的小工具，而是优化目标的可执行定义。

一个严格的教学版本只允许单个 ASCII 整数字符串：

```python
import re

def verify_integer(text, expected):
    if len(text) > 100:
        return False
    normalized = text.strip()
    if re.fullmatch(r"[+-]?[0-9]+", normalized) is None:
        return False
    return int(normalized) == expected

tests = {
    "42": True,
    "  +42 ": True,
    "答案是42": False,
    "41,42,43": False,
    "42\n99": False,
    "": False,
}
for text, expected_result in tests.items():
    assert verify_integer(text, 42) == expected_result
```

它牺牲了自然回答的灵活性，换来一个容易审计的小目标。真实任务若需要解释，应明确定义结构化输出，再分别解析解释和答案，不能只把正则表达式放宽到“总能找到一个数字”。

## 奖励组合会改变最优行为

常见设计把正确性、格式与成本相加：

$$
R=\alpha R_{\mathrm{correct}}
+\eta R_{\mathrm{format}}-\lambda C.
$$

假设正确性奖励为 1，格式奖励为 0.2。一个始终格式正确却答错的策略可拿 0.2；另一个只有一半概率答对、但格式总不合要求的策略，奖励如何计算取决于正确性验证是否依赖格式解析。不能在纸面上把这些项当作彼此独立。

如果格式奖励容易获得、正确答案非常稀疏，早期梯度可能主要优化格式。这有时是有意的课程设计，但必须同时记录各奖励分量，防止总分上升掩盖正确率停滞。

长度惩罚也有类似问题。两条回答都正确，一条更短，适度成本可以提升效率；若惩罚过强，模型可能倾向尽早结束、猜答案或者避免展开必要步骤。应报告相同质量水平下的长度与成本，而不是只看平均 token 数下降。

## 结果奖励与过程监督回答不同问题

结果奖励只告诉模型这次是否成功，便宜但稀疏，也难以确定哪些中间动作有贡献。过程监督试图评价中间步骤，可以提供更细信号，却增加标注成本与局部判分误差。[Let's Verify Step by Step](https://arxiv.org/abs/2305.20050)研究了数学推理中的过程监督，不意味着每个被判为正确的局部步骤必然组成全局正确证明。

一个教学例子是两步计算：第一步错误地把 3×4 算成 10，第二步又错误地加 2，最终碰巧得到 12。只验结果会给满分，过程验证会发现问题。反过来，使用不同但正确的解法，如果过程验证器只接受标准步骤，也可能误判。

因此要区分“答案是否正确”“过程是否可信”和“策略是否能在新题上稳定成功”。它们可以相关，但不是同一个指标。

## 奖励投机是一种优化后的分布变化

验证器在随机样本上只有很小错误率，并不能保证经过长期优化后仍然可靠。策略会逐渐集中到高分输出，其中可能包括解析漏洞、测试集盲点与格式捷径。

例如训练测试只包含正整数，生成的程序可以对负数错误但仍满分；若测试输入暴露在提示中，策略可能直接返回缓存答案。解决方式不是单纯“增加一点惩罚”，而是改善验证覆盖、隔离测试信息、设置隐藏测试，并检查策略是否依赖偶然规则。

[奖励过度优化研究](https://arxiv.org/abs/2210.10760)主要研究代理奖励的优化失真。它为这里提供了一个通用警示：训练奖励持续增长时，应使用独立标准检查真实目标；不能把该论文的具体曲线直接移植成 RLVR 的统一规律。

## 验证器本身也要有测试集

给验证器准备四类案例：明确正确、明确错误、边界格式、针对解析规则的对抗输出。数学任务还应覆盖等价表达、单位、精度与不唯一答案；代码任务应覆盖边界输入、随机测试和资源限制。

若将模型生成程序投入运行，需要独立沙箱、文件和网络权限限制、进程与内存限制以及超时清理。一个 Python 子进程或容器名称本身不是完整安全边界。本文的小实验刻意只比较字符串与整数，因此不需要执行不可信代码。

验证器版本必须写入样本元数据。同一回答在新旧验证器下得分不同，会让训练曲线出现跳变；如果没有版本号，很容易误把规则变化当成模型进步。

## 在个人主机上做一次漏洞回归

先实现一个故意脆弱的验证器，例如只检查答案字符串是否出现在输出中；准备包含正确答案列表、额外数字、空答案、超长文本和相似 Unicode 字符的样本。再与严格版本逐项比较，统计假阳性和假阴性。

第二步生成加减法题，将题目按运算结构而不是随机行划分：训练只含两项运算，测试加入负数与三项运算。用一个手写候选生成器产生正确、计算错误和格式错误回答，观察不同奖励权重会优先选择哪种候选。这是验证奖励合同的模拟，不是 RL 模型性能实验。

验收标准是每个规则都有至少一个正例和反例；漏洞修复后历史反例不能再次通过；训练评分与独立评分分别统计；失败案例能定位到生成、解析、规则或环境；没有把“验证器接受”直接写成“现实任务完全正确”。
