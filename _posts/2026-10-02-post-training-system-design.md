## 先把算法画成有状态的数据流

SFT 主要读取监督数据并更新模型；离线偏好优化读取固定偏好对，还可能使用参考模型；在线策略优化通常还要生成轨迹、评分、计算优势或其他训练信号，再执行策略更新。某些算法需要价值模型，另一些不需要，系统不能为了套一个统一架构而增加无关角色。

把一次在线迭代写成具体数据流更容易发现依赖：提示进入采样器，采样器使用某个版本的策略生成回答，评分器返回奖励，训练器消费轨迹并得到新策略，随后把新权重提供给下一轮采样。每条边都应有数据格式、版本和容量约束，而不是只用“调用模型”概括。

[HybridFlow 原论文](https://arxiv.org/abs/2409.19256)讨论了后训练中多模型、多阶段执行的组织问题；[verl 编程指南](https://verl.readthedocs.io/en/latest/hybrid_flow.html)展示了控制器、角色和资源池的划分。这些资料提供设计参考，不意味着所有后训练任务都需要同样数量的模型或进程。

## 轨迹是训练数据，也是版本化的系统对象

一条轨迹至少应标识提示、生成 token、有效位置 mask、策略版本、生成配置与评分版本。需要旧策略概率的算法，还必须保存或可靠重建生成策略对应的 log probability。只保存文本再用当前策略重新算一遍，可能已经失去算法要求的“旧策略”含义。

长度处理也影响目标函数：截断、EOS、padding 和模板中的 token，哪些计入奖励、概率和损失，必须一致。若采样器和训练器使用不同的 tokenizer 或 chat template，看起来相同的文本可能变成不同 token 序列。模型权重校验和相同，也不能保证整个数据解释过程相同。

可把轨迹身份定义为请求 ID 加尝试编号，训练批次另外记录接受了哪些轨迹。失败重试可能产生不同回答，不能把重复消息自动当作可互换副本。去重规则应保证一个已提交训练批次不会在恢复后再次应用，而不是仅保证日志里没有相同字符串。

## 用容量模型决定角色怎么放置

设 rollout 每轮需要 40 秒，评分 10 秒，训练更新 20 秒，权重转换和同步 5 秒。完全串行的纸面迭代时间为 75 秒。若使用独立资源池并允许合法的流水处理，稳态节拍可能受最慢阶段的 40 秒限制；但这不是免费加速，需要足够缓冲、独立资源，并解决版本滞后。

角色共置可以复用设备，降低闲置资源，但阶段切换时可能涉及权重格式转换、显存释放和缓存重建。角色分离可以并行工作，却会占用更多设备，并需要传输权重与轨迹。部署前应列出各阶段峰值显存、工作时长、数据量和依赖，而不是先按 GPU 数均分资源。

如果生成每秒提供 120 条轨迹，而训练器每秒只能消费 80 条，队列将以每秒 40 条增长。缓冲 400 条只能延缓约 10 秒，并没有修复吞吐不匹配。系统需要背压、准入或调整阶段资源；无限扩展队列会增加显存或主机内存压力，也让数据越来越陈旧。

## 异步增加吞吐，也引入策略滞后

同步方案在本轮轨迹完成后更新，再让下一轮使用新策略，版本关系比较清楚。异步方案允许旧版本轨迹在新策略已发布后继续到达，可以减少等待，却改变数据与当前策略的距离。

例如训练器已经更新到版本 12，队列中仍有版本 8 的轨迹。是否可接受，取决于算法与配置；不能仅把版本号改成 12。可定义最大滞后、丢弃策略、重要性权重等机制，但它们都需要算法层面的理由和质量验证。

调度器应能回答“哪个版本正在被哪个 worker 使用”，权重发布也应有确认协议。文件传输完成不一定表示推理引擎已经激活新版本；旧请求是否继续使用旧权重、新请求何时切换，都必须有清晰边界。尤其在共享缓存时，权重身份变化要与缓存有效性配合。

## 可观测性要同时连接质量与系统行为

一组指标观察资源和吞吐：阶段耗时、队列长度、有效 token/s、设备显存、通信量、权重同步耗时与失败重试。另一组指标观察学习过程：奖励分布、输出长度、KL 或其他约束项、梯度范数、损失与独立评估成绩。

这两组必须能按同一 run、配置和策略版本关联。奖励突然上涨，可能来自模型能力变化，也可能来自输出截断、评分版本更换或短回答比例变化。仅保留一个平均 reward，既无法排查算法，也无法排查系统。

[OpenTelemetry 信号说明](https://opentelemetry.io/docs/concepts/signals/)区分了指标、日志与链路追踪：指标适合看趋势，日志记录具体事件，trace 串联一次请求穿过各阶段的耗时。轨迹 ID 不宜无节制地成为高基数指标标签，更适合在日志和 trace 中关联；同时只记录排障需要的数据，避免完整文本无限复制。

## 个人主机实验：验证版本准入与队列背压

先用标准库构造一个调度模型，无需运行大模型。下例把“允许的策略滞后”和“队列容量”当成明确的系统规则；数值仅用于教学，并非推荐的训练超参数。

```python
from collections import deque

current_version = 12
max_lag = 2
capacity = 3
queue = deque()
seen = set()

def admit(trajectory):
    key = trajectory["id"]
    lag = current_version - trajectory["policy_version"]
    if key in seen:
        return "duplicate"
    if not 0 <= lag <= max_lag:
        return "version_rejected"
    if len(queue) >= capacity:
        return "backpressure"
    queue.append(trajectory)
    seen.add(key)
    return "accepted"

assert admit({"id": "a", "policy_version": 8}) == "version_rejected"
assert admit({"id": "b", "policy_version": 11}) == "accepted"
assert admit({"id": "b", "policy_version": 11}) == "duplicate"
assert admit({"id": "c", "policy_version": 12}) == "accepted"
assert admit({"id": "d", "policy_version": 12}) == "accepted"
assert admit({"id": "e", "policy_version": 12}) == "backpressure"
```

验收不止是断言通过。先让训练版本推进到 15，再检查已经排队的版本 11 轨迹是否仍满足规则；这说明消费时也可能需要验证，而不能只在入队时判断。再模拟入队成功但确认消息丢失后的重试，确认不会重复消费。示例的 seen 只保存在内存中，不能提供崩溃后的持久去重保证，真实系统需要与批次提交一起设计。

最后加入模拟时钟，为生成、评分和训练设置不同速率，验证当生产快于消费时队列是否触发背压。这个实验能检验状态机和容量计算，不代表任何真实 RLHF 系统的训练速度或收益。

## 用一个可恢复的小闭环作为最终验收

先固定数据和初始化，完成“采样、评分、更新、保存、恢复、独立评估”的最小闭环，再逐个替换组件。检查点应把策略、必要辅助状态、数据进度和已提交批次关联到同一逻辑时刻。具体状态清单可沿用 [检查点恢复](/posts/ai-infra/checkpoint-recovery/) 中的事务边界。

每次实验保存完整配置、数据与模型身份、随机状态或种子策略、依赖和硬件信息，并明确比较的是系统吞吐还是最终质量。[PyTorch 可复现性说明](https://docs.pytorch.org/docs/stable/notes/randomness.html)提醒我们，跨平台与版本不能轻易承诺逐位一致。

最终报告应能回答：一次更新使用了哪些轨迹和策略版本，失败后会重做哪部分，吞吐受哪个阶段限制，质量变化是否超出随机波动。能够回答这些问题，才说明组件已经形成一个可解释、可恢复、可持续改进的后训练系统。
