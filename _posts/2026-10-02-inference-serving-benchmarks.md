## 服务性能必须从用户看到的请求开始

离线生成最大 token/s，与在线请求及时返回，是不同的优化目标。大 batch 可以摊薄权重读取与调度成本，却可能让新请求排队更久。一个服务即使总输出吞吐提高，也可能让多数用户等待首字更久，或者在生成中间遇到明显停顿。

因此压测首先要定义负载：输入长度、目标输出长度、请求到达过程、共享前缀比例、采样参数和停止条件。两个模型使用不同分词器时，相同字符数也不代表相同 token 工作量。若一组请求大多提前 EOS，另一组都生成到上限，直接比较 token/s 或每请求延迟很容易得出错误结论。

精度、量化、并行配置和版本也应随结果保存。性能改动可能影响质量，压测通过不等于输出质量通过；至少应保留任务层面的质量验收，避免把更短的错误回答解释为系统提速。

## 分开记录首 token 与后续 token

用客户端发送时刻 t₀、收到第一个输出 token 的时刻 t₁，以及后续时刻 t₂ 至 tₙ 定义：

$$
TTFT=t_1-t_0,\qquad ITL_i=t_i-t_{i-1}.
$$

若输出有 n>1 个 token，常用平均输出 token 时间为：

$$
TPOT=\frac{t_n-t_1}{n-1}.
$$

TTFT 可以包含客户端到服务端传输、排队、prefill 和首 token 生成；服务端内部记录的 TTFT 可能从不同边界开始。ITL 是相邻输出间隔，TPOT 是一个请求内后续生成的平均速度，两者不能互换。只有一个输出 token 时，TPOT 没有这个定义，应明确标为不适用。

纸面例子：请求在 0 秒发送，token 到达时刻为 0.8、0.9、1.0、1.7 秒。TTFT 为 0.8 秒，三个 ITL 为 0.1、0.1、0.7 秒，TPOT 为 0.3 秒。平均生成速度掩盖了最后一次长停顿。网络分块可能一次携带多个 token，因此真实客户端应记录流事件与 token 计数，不能把每个网络 chunk 无条件当成一个 token。

## 开环与闭环压测回答不同问题

闭环压测保持固定并发：一个请求结束才发送新的请求。服务变慢时，实际到达率自动下降，适合观察固定并发下的吞吐，却可能掩盖外部流量持续到达时的队列增长。

开环按预定时间发送请求，服务变慢时仍继续到达，更适合寻找负载拐点。达到服务能力上限后，队列会持续增长；若压测只测很短时间，可能尚未观察到真实尾部。请求率、实际发送率、完成率和错误率都要一起报告，不能只写一个目标 QPS。

还要避免客户端自身成为瓶颈。客户端 CPU、连接池或最大并发限制可能拖延原定发送时间，这属于客户端排队，应单列而不是消失在统计里。[vLLM bench serve 文档](https://docs.vllm.ai/en/latest/cli/bench/serve/)区分了请求率与最大并发，并提供延迟分位数和详细结果选项；具体参数应以已安装版本的帮助为准。

## Goodput 把服务目标放回吞吐定义

设观察窗口长 W 秒，成功完成且同时满足全部延迟目标的请求数为 N_good，则请求 goodput 定义为 N_good/W。它与成功请求吞吐、输出 token 吞吐是不同口径，必须注明单位和窗口边界。

例如某个构造场景在 100 秒内完成 1000 个成功请求，其中 700 个同时满足 TTFT≤1 秒、TPOT≤50 毫秒。成功吞吐是 10 请求/秒，goodput 是 7 请求/秒。另一个配置完成 1200 个，但只有 600 个达标，吞吐更高而 goodput 更低。[DistServe 原论文](https://arxiv.org/abs/2401.09670)以受服务目标约束的 goodput 为重要优化目标。

不能分别统计“90% 请求满足 TTFT”和“90% 满足 TPOT”，就断言 90% 同时满足；两个集合可能只部分重叠。也不能把所有 token 的 ITL 混在一起后，用一个全局 P99 替代每请求 TPOT 目标。不同聚合层级会对长回答和短回答赋予不同权重。

## 批处理策略会改变不同阶段的等待

静态 batch 常被最长请求拖住，连续批处理允许已完成请求离开、新请求加入，提高资源使用灵活性。但大量长 prefill 若占据执行窗口，已有 decode 请求仍可能出现间隔抖动。分块 prefill、调度优先级或阶段拆分，可以改变这种干扰，同时引入新的调度和传输代价。

因此压测矩阵至少应包括短输入短输出、长输入短输出、短输入长输出以及混合长度。再分别测试冷缓存与有共享前缀的负载，避免高缓存命中率掩盖一般请求的成本。服务内部的排队、运行请求和缓存状态，能帮助解释客户端观察到的变化。[vLLM 指标设计文档](https://docs.vllm.ai/en/latest/design/metrics/)提供了理解服务观测口径的背景。

## 观察窗口与未完成请求决定统计是否诚实

假设压测连续发送六十秒，最后一批请求又花三十秒才全部完成。若把所有完成请求除以六十秒，会把排空阶段的计算免费计入吞吐；若只统计前六十秒完成的请求，又可能遗漏最慢的那部分。两种口径可以分别服务不同分析，但必须明确说明分子对应哪个请求集合、分母包含哪段时间。

一种简单做法是报告完整实验墙钟时间、发送窗口和排空时间，同时保留按发送批次归属的请求延迟。稳态分析可以选择中间稳定时段，但应同时显示队列是否持续增长；在不断积压的系统里截取一个短窗口，不能称为稳定承载能力。

超时、取消和网络错误也不能从延迟样本里无声消失。成功请求的尾部可能看起来很好，只是最慢请求已经被超时机制移走。应单独报告这些结果的数量和比例，并明确它们不会进入达标 goodput。重试则是新的一次系统负载，也会消耗资源，不能只保留最终成功尝试而忽略前面的成本。

分位数需要足够样本。几十个请求中的百分之九十九分位往往接近最大值，对单个异常非常敏感。若要稳定比较尾部，应增加观测样本并重复实验，而不是输出更多小数位。不同统计库的插值方法也可能不同，报告中保存原始数据和分位数算法，才能让结果可复算。

## 个人主机实验：用人工时间戳验证统计器

在接入真实服务之前，先证明统计代码不会把失败或不达标请求计入 goodput。下面的数据完全是构造样本，不是任何模型的压测结果。

```python
requests = [
    {"sent": 0.0, "tokens": [0.4, 0.45, 0.50], "ok": True},
    {"sent": 0.0, "tokens": [1.2, 1.25, 1.30], "ok": True},
    {"sent": 0.1, "tokens": [0.6, 0.9, 1.2], "ok": True},
    {"sent": 0.2, "tokens": [], "ok": False},
]

def metrics(request):
    tokens = request["tokens"]
    if not request["ok"] or len(tokens) < 2:
        return None
    ttft = tokens[0] - request["sent"]
    tpot = (tokens[-1] - tokens[0]) / (len(tokens) - 1)
    return ttft, tpot

good = 0
for request in requests:
    result = metrics(request)
    if result is not None:
        good += result[0] <= 1.0 and result[1] <= 0.1
assert good == 1
window_seconds = 2.0
print("goodput requests/s", good / window_seconds)
```

验收标准是能手算唯一达标请求，区分第二条的首 token 超时与第三条的后续生成缓慢，并确认失败请求仍在总请求统计中。再加入仅一个 token 的成功请求，先定义它的达标策略，再修改统计器，不能默默把未定义的 TPOT 当成零。

扩展实验可在本地主机用一个只按预设延迟输出文本的模拟服务验证压测客户端。它只能验证调度、计时和统计链路，不能用于评估大模型硬件性能。真正的性能报告应保存逐请求记录、失败原因、客户端排队与实际 token 数，并说明观察窗口是否包含排空阶段。

有可用服务后，逐级提高到达率，观察 P50、P95、P99、错误率和 goodput 的共同变化，找到服务目标开始稳定失守的位置。把这条曲线与内部队列和缓存指标对应起来，比展示单个峰值 token/s 更能说明系统实际承载能力。
