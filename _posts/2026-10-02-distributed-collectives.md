## 先问通信结束后，每个进程拥有什么

分布式通信最容易混淆的地方，是把“数据传到了哪里”和“数据做了什么运算”混为一谈。rank 是通信组里的进程编号，不必等于机器编号。假设三个 rank 分别拥有向量 `[1,2]`、`[3,4]`、`[5,6]`，求和 AllReduce 结束后，每个 rank 都得到 `[9,12]`。它包含跨进程求和，也包含结果复制；平均梯度还需要正确的除法语义。

AllGather 不求和，而是按 rank 顺序拼接，所有进程得到 `[1,2,3,4,5,6]`。ReduceScatter 则先规约，再让每个 rank 只保留结果的一片。AlltoAll 更像定向分发：每个发送者给不同接收者不同片段，常见于专家路由。选择操作前，先画出输入与输出的所有权，比先猜哪个 API 更快可靠。[NCCL 集合操作文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)明确给出了这些操作的结果布局与参与约束。

例如，数据并行需要每个副本获得相同的完整梯度，AllReduce 很自然；分片优化器只更新自己拥有的参数片段，ReduceScatter 可以避免让每个 rank 长期保存完整梯度。通信模式因此是状态布局的结果，而不是可以脱离算法任意替换的零件。

## 一个有边界的延迟模型

把一次消息的耗时近似写成启动延迟加传输时间：

$$
T(n)=\alpha+\frac{n}{B}.
$$

这里 n 是字节数，B 是该通信路径上的有效字节带宽，α 包含协议和调度等固定成本。它不是硬件说明书的峰值模型：真实传输还会受到拥塞、分块、同步和计算竞争影响。这个简化式的价值在于解释尺度变化。

假设 α 为 8 微秒，B 为 25 GB/s，全部采用十进制单位。4 KB 消息的传输项仅为 0.16 微秒，总计约 8.16 微秒；100 MB 消息的传输项是 4 毫秒。前者优化启动次数更重要，后者优化有效带宽更重要。把小消息吞吐换算成 GB/s 再与网卡峰值比较，往往只是在度量固定延迟占比。

对 p 个 rank、每个 rank 有 n 字节输入的理想环形 AllReduce，可把过程拆为 p−1 轮 ReduceScatter 和 p−1 轮 AllGather。每轮发送 n/p 字节，于是有：

$$
T_{ring}\approx2(p-1)\alpha+\frac{2(p-1)n}{pB}.
$$

这不是 NCCL 始终使用环形算法的断言，而是一个可验证的分析模型。令 p=8、n=1 GB，沿用前面的参数，估计时间约为 70.112 毫秒。每个 rank 发送的逻辑数据量约为 1.75 GB。p 增大时，大消息项逐渐接近 2n/B，延迟项却持续增长，这解释了为什么增加设备并不会让所有集合通信都变快。

## 为什么测出来的“带宽”有两个数

输入大小除以耗时得到算法带宽，但它不等于链路实际承载的数据率。对环形 AllReduce，常见的归一化总线带宽会再乘 2(p−1)/p。使用上例，算法带宽约为 14.26 GB/s，而按此口径换算的总线带宽接近 24.96 GB/s。它们描述的是同一次操作，不能直接互相排名。[NCCL Tests 的性能说明](https://raw.githubusercontent.com/NVIDIA/nccl-tests/master/doc/PERFORMANCE.md)解释了不同集合操作的换算方法。

写性能记录时应一起保留操作类型、rank 数、消息大小、数据类型、计时范围和带宽口径。只有“通信达到 20 GB/s”这一句话，读者无法知道测试是否跨节点，也无法复算结果。还要区分每个 rank 的大小、所有 rank 输入总和，以及计入发送还是发送加接收；三个口径混用，误差可能达到设备数量的倍数。

## 拓扑决定哪些字节昂贵

两台机器各四张 GPU 时，节点内部互联与节点之间网络的成本往往不同。分层思路是先在节点内规约，再让节点代表交换结果，最后在节点内分发。这样可能减少慢链路上的重复流量，但具体收益取决于算法、网卡数量、GPU 与网卡亲和性和并发任务，不能只按机器数量推断。

特别要关注共享上行链路：两条逻辑通信路径可能竞争同一物理链路。把它们的独立测试峰值相加，会高估并发能力。NUMA、PCIe 路径和网络接口选择也可能让外观相同的 GPU 走不同路径。遇到明显不对称时，应先保存拓扑、接口和运行日志，再讨论调大通信桶。[NCCL 排障入口](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting.html)可用于沿互联和环境配置继续排查。

通信与计算还可能重叠。若反向传播持续 100 毫秒，其中前 60 毫秒已覆盖了 50 毫秒通信，不能把整段通信时间再加到步骤时间上。真正需要降低的是最后拖住优化器更新的那段通信尾部。缩小桶有机会更早启动，却增加启动次数；增大桶减少次数，又可能推迟第一个可发送时刻。

## 个人主机实验：验证语义与估算，而非模拟集群速度

下面只用 Python 标准库验证“规约后分片，再聚合”等价于完整规约，并计算理论时间。列表切片没有网络成本，因此程序运行时间没有 GPU 通信性能含义。

```python
inputs = [[1, 2, 3, 4], [10, 20, 30, 40]]
reduced = [sum(xs) for xs in zip(*inputs)]
shards = [reduced[:2], reduced[2:]]
gathered = [x for shard in shards for x in shard]
assert gathered == [11, 22, 33, 44]

def ring_seconds(nbytes, ranks, latency, bandwidth):
    return 2 * (ranks - 1) * latency + (
        2 * (ranks - 1) / ranks * nbytes / bandwidth
    )

for n in [4_000, 1_000_000, 1_000_000_000]:
    print(n, ring_seconds(n, 8, 8e-6, 25e9))
```

验收标准是可以解释三个输出为什么不随消息大小严格成比例，并能在不运行代码的情况下算出大消息的近似值。再将 rank 数改为 2、4、16，分别观察固定项与传输项；检查单位变换是否把 Gb/s 错当成 GB/s。若将 α 设为零，小消息应失去启动开销，这个反事实检查能发现公式抄写错误。

有真实集群时，再增加独立的性能实验：先预热，扫描消息大小，重复多次并记录分布，最后比较同节点和跨节点。各 rank 必须以兼容的顺序调用集合操作；某个 rank 提前退出、张量长度不一致或分支里漏掉一次调用，都可能表现为其他 rank 卡住。此时等待时间是正确性问题的症状，不能当成“带宽突然下降”。

本文的公式和示例都是纸面分析，未宣称任何设备实测成绩。学会从数据所有权、消息尺度和物理路径逐层推导，才有依据判断下一次优化应该改变算法、消息组织还是部署位置。
