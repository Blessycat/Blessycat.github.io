## 先建立显存账本，避免拿参数文件大小估计训练需求

一份十亿参数的 BF16 权重约占 2 GB，但完整训练不只保存这一份权重。为了演算，假设参数和梯度各用 2 字节，优化器有一份 FP32 主权重，以及两个 FP32 动量状态，共 12 字节。则模型状态合计每参数 16 字节，十亿参数约 16 GB。这里采用十进制 GB，且明确假设存在主权重；具体优化器和混合精度实现可能不同。

激活、注意力临时结果、通信缓冲、内存分配器保留空间和框架开销都尚未计入。因此“16 GB 状态能放进 16 GB 显卡”并不成立。应把状态账本与运行峰值分开记录：账本帮助解释量级，峰值决定训练是否会溢出。

数据并行每个 rank 都保存同样的状态，重复量随副本数增加。ZeRO 的核心思路是让副本在处理不同数据时，只长期持有训练状态的一部分，需要时再交换信息。[ZeRO 原论文](https://arxiv.org/abs/1910.02054)提出了逐步消除这些冗余的设计。

## 三个阶段分别切分什么

令 P 为参数数目，R 为分片 rank 数，沿用每参数 2 字节权重、2 字节梯度、12 字节优化器相关状态的假设，得到以下理想持久状态估算：

| 布局 | 每个 rank 的状态字节数 | P=10 亿、R=8 |
|---|---:|---:|
| 普通数据并行 | 16P | 16 GB |
| ZeRO-1 | 4P + 12P/R | 5.5 GB |
| ZeRO-2 | 2P + 14P/R | 3.75 GB |
| ZeRO-3 | 16P/R | 2 GB |

第一阶段切优化器状态，第二阶段再切梯度，第三阶段连参数也切。数值不包含临时重建和激活，不能直接作为显卡采购建议。[DeepSpeed ZeRO 教程](https://www.deepspeed.ai/tutorials/zero/)说明了阶段与卸载能力，实际配置还应绑定运行环境的版本。

ZeRO-1 的直觉是每个 rank 只负责更新自己那一片参数的优化器状态，再让副本获得更新后的完整参数。ZeRO-2 不再要求每个 rank 长期保留完整梯度。ZeRO-3 则连前向需要的权重也可能临时重建。分片程度越高，持久冗余越小，但状态的取回和释放越频繁。

FSDP 与 ZeRO-3 在“完整分片训练状态”的目标上相关，却不是同一个 API 或完全相同的执行实现。也不能把旧版 FSDP 的配置字段直接复制到新版接口。当前 PyTorch 的 [fully_shard 文档](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html)描述了基于模块的分片，以及前向后是否重新分片的行为。

## 沿一层的生命周期观察峰值

把 Transformer 按 block 划成分片单元。运行某个 block 前，AllGather 将参数片段恢复为可用于计算的完整权重；前向结束后可以释放完整副本。反向需要参数时再取回，梯度通过 ReduceScatter 留下本 rank 负责的片段。优化器只更新本地拥有的状态。

如果前向后保留完整参数，反向可以少一次重建，但要让更多完整权重在显存中存活。若立即重新分片，显存较低，却增加通信需求。预取下一层还能覆盖一部分等待时间，同时让当前层与下一层的权重暂时共存。于是峰值是时间线上活跃对象的总和，不是静态表格中最大的单个项目。

例如某布局持久状态 2 GB，最大分片单元完整权重 0.6 GB，激活峰值 3 GB，通信和运行缓冲估计 0.8 GB。若本地已包含该单元八分之一的权重，重建额外开销近似为 0.525 GB，合计约 6.325 GB；如果实现需要额外完整缓冲，或同时预取下一单元，峰值还会更高。这是带假设的纸面账本，不是 FSDP 保证值。

分片单元过大，单次重建峰值和暴露在关键路径上的等待都可能很大；过小，集合操作次数和启动成本增多。合理粒度需要同时考虑模型层大小、计算持续时间和互联性能。不要认为按每个小 Linear 包装就必然最省显存或最快。

## 省显存的方法处理的是不同对象

激活检查点通过反向时重算部分前向来减少保留的激活，通常增加计算；状态分片处理跨副本冗余，通常增加或改变通信；CPU 卸载把部分状态移出 GPU，增加主机内存需求与传输压力。它们可以组合，但成本并不会相互抵消。

尤其是梯度累积。DDP 中延迟同步主要影响梯度通信，而全分片训练还必须取回前向需要的参数。简单套用 `no_sync` 的直觉，可能导致完整梯度或参数长时间保留，意外提高显存。应依据所用 FSDP 版本的累积接口与生命周期来设计，并在完整累积窗口测量峰值。

还需区分显存分配与保留：框架可能缓存释放后的内存供后续复用，所以工具显示的进程占用未下降，并不自动代表对象没有释放。判断优化是否有效，要比较相同输入、相同预热状态下的峰值已分配空间、峰值保留空间以及是否存在大块分配失败。

## 通信与卸载也应该有自己的账本

假设一个分片单元的完整权重为六百兆字节，八个 rank 各自持有八分之一。一次重建需要每个 rank 接收其余七份，逻辑接收量约为五百二十五兆字节。如果有效接收带宽假定为每秒二十五吉字节，仅传输项就约为二十一毫秒，还没有计算启动延迟与竞争。若该单元计算仅持续五毫秒，仅靠附近的计算就难以把这次等待完全遮住。

这提示两个不同方向：扩大单元中的可用计算量，或者改变参数保留与预取方式。前者可能提高算子效率却抬高重建峰值，后者可能减少重复通信却增加活跃显存。不能只优化某个单独指标；应在同一张时间表上比较状态数量、传输时刻与计算依赖。

CPU 卸载也可以先算下界。若每次更新必须搬运八吉字节，而可用通路有效带宽假设为每秒十六吉字节，仅一趟传输就需要半秒。即使显存问题解决了，若原先计算只需一百毫秒，卸载可能成为主导成本。双向传输、主机优化器计算和内存带宽还会进一步影响结果，因此纸面估算的作用是筛选明显不合适的方案，而不是替代测量。

最终比较应固定训练工作量，列出是否能运行、峰值空间、稳态更新时间和启动成本。有时更激进的分片让单步变慢，却允许更长序列或更大微批，整个任务的有效吞吐反而提高；这属于工作配置变化，应与相同配置下的纯系统加速分开解释。

## 个人主机实验：让分片账本可复算

无需下载模型，标准库脚本就能检查假设之间的关系：

```python
def state_gb(params, ranks):
    return {
        "ddp": 16 * params / 1e9,
        "zero1": (4 + 12 / ranks) * params / 1e9,
        "zero2": (2 + 14 / ranks) * params / 1e9,
        "zero3": 16 * params / ranks / 1e9,
    }

assert state_gb(10**9, 8)["zero2"] == 3.75
for ranks in [1, 2, 4, 8, 16]:
    print(ranks, state_gb(10**9, ranks))

def extra_gather_gb(unit_gb, ranks):
    return unit_gb * (1 - 1 / ranks)
print("extra gathered weights", extra_gather_gb(0.6, 8))
```

验收时检查 R=1 是否全部回到 16 GB；R 逐渐增大时，ZeRO-1 是否仍留下完整参数和梯度的下界；去掉假设中的主权重后，是否重新推导了所有阶段，而非只改总数。再用一个手写时间表列出“层 A 重建、层 B 预取、层 A 激活仍在”的共存区间，计算峰值随预取变化的方向。

已有 GPU 环境的读者可以用很小的模型进一步验证，但应先做单次前向、单次更新，再做完整累积窗口。记录 batch、序列长度、精度、分片粒度、预取和检查点设置，同时比较训练损失与未分片基线。验收不仅是“不再 OOM”，还包括更新正确、吞吐没有被通信或卸载压到不可用，以及保存恢复能够保持状态对应。

选择布局的顺序可以很朴素：先找出峰值里最大的对象，再选择针对它的机制；确定能放下以后，再测暴露通信与计算重叠。把所有省显存开关一起打开，会让问题来源和性能代价都难以解释。
