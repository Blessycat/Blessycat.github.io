## 工具调用把一次回答变成一次交互

普通问答常可表示为提示到回答的映射。工具型 agent 则会发出动作、接收环境观察，再决定下一步。一次计算任务可能经历“选择计算器—提交参数—读取结果—组织最终回答”。

训练对象因此不只是一段好文本，而是一条包含动作与观察的轨迹。[ReAct](https://arxiv.org/abs/2210.03629)展示了交替进行推理与行动的交互方式；[Toolformer](https://arxiv.org/abs/2302.04761)探索了自动构造工具使用数据。二者的目标和数据生成方法不同，不能因为都调用工具就当成同一种后训练算法。

更关键的区别是：模型选择工具名和参数，工具返回值由环境决定。把这两种 token 混为模型行为，会直接影响监督损失、策略梯度和奖励归因。

## 轨迹应该保留哪些字段

一个最小动作记录包含工具名称、结构化参数、调用编号、执行状态与结果。完整训练样本还应保留动作发生前的可见历史、工具 schema 版本、环境初始状态、结束原因、错误类别、模型版本和奖励版本。

例如模型提交加法参数 a=17、b=25，环境返回 value=42。训练“正确发起调用”时，需要让模型学习输出工具名和参数；训练“使用工具结果”时，工具返回值作为上下文，模型学习生成最终回答。

如果把整段日志直接拼接后对所有 token 做 next-token loss，模型还会被要求预测环境输出。某些联合建模研究可能有意这样做，但那是不同目标。常见的动作模仿训练应明确 mask，只对模型应产生的内容计算损失。

同理，强化学习中的 log probability 只属于策略实际采取的动作。工具返回的网页、数据库内容或计算结果没有对应的策略选择概率，不应被累加进 PPO 或 GRPO 的回答动作概率里。

## 监督数据不能偷看未来

设轨迹的第二步工具结果已经出现。训练第一步调用时，只能使用当时可见的前缀，不能把未来结果提前塞入提示。否则模型学会的是“看到答案后补写调用”，部署时却必须在不知道答案的条件下行动。

成功轨迹也不一定是好示范。一个 agent 可能先调用五个无关工具，再碰巧成功；直接模仿会复制浪费。筛选时应同时评价最终结果、动作必要性、参数正确性和成本。

失败轨迹则有不同用途：可以用于偏好比较、错误恢复示范或奖励学习，但不宜未经处理就把整条失败动作当成正向 SFT 标签。恢复示范应明确从哪个错误状态开始，以及后续动作为什么能够修复问题。

工具异常也要分开记录。模型参数错误、schema 不匹配、环境超时和工具内部故障不是同一种失败。若把全部异常都记为“模型答错”，策略可能学会逃避本来有用但偶尔不稳定的工具。

## 信用分配比最终打分更细

假设最终任务成功奖励为 1，每次工具调用成本为 0.1。使用一次必要工具后成功，总回报为 0.9；使用三次后成功，为 0.7。这个设计鼓励有效调用，但若成本过高，也可能鼓励直接猜答案。

对多步轨迹，可写折扣回报：

$$
G_t=\sum_{k=t}^{T}\gamma^{k-t}r_k.
$$

终局奖励会传回较早动作，但不能自动识别“哪一步真正导致成功”。如果一条轨迹包含正确检索、错误计算和偶然猜中，所有动作都可能共享较好的最终回报。价值估计、过程奖励与反事实对照可以帮助分析，但每一种都引入额外假设。

过程奖励例如“工具调用格式合法”容易验证，却可能让策略反复调用无用工具刷分。更好的检查是区分合法性、必要性与结果贡献，并观察成本与成功率的联合变化，而不是把所有中间正反馈相加后只看总分。

## 一个本机模拟工具环境

```python
import math

def dispatch(action):
    if not isinstance(action, dict) or action.get("name") != "add":
        return {"ok": False, "error": "unknown_tool"}
    args = action.get("arguments")
    if not isinstance(args, dict) or set(args) != {"a", "b"}:
        return {"ok": False, "error": "bad_arguments"}
    values = [args["a"], args["b"]]
    if any(type(v) not in (int, float) or abs(v) > 1000000
           or not math.isfinite(v) for v in values):
        return {"ok": False, "error": "bad_number"}
    return {"ok": True, "value": sum(values)}

good = {"name": "add", "arguments": {"a": 17, "b": 25}}
bad = {"name": "add", "arguments": {"a": "17", "b": 25}}
assert dispatch(good) == {"ok": True, "value": 42}
assert dispatch(bad)["error"] == "bad_number"
```

这个环境只允许一个显式工具，不用 eval，也不把输入字符串拼成 shell 命令。它展示的是工具边界检查，而非完整安全沙箱。真实执行代码、浏览网页或修改文件，需要额外的权限、资源与隔离机制。

CPU 实验可以构造三种表格策略：总是猜答案、总是调用一次加法、先无效调用再正确调用。对合成题运行同样数量的回合，记录任务成功率、调用数、非法参数率与回报。改变调用成本，观察哪种策略被奖励函数偏好。

## 沙箱是环境设计的一部分

用于训练的环境应可重置，让同一任务从可比较的初始状态开始。网络、文件、进程和账户权限必须与任务所需范围一致；状态修改最好支持回滚，工具超时后应能终止残留工作。仅仅把模型输出放进子进程，并不能保证隔离。

观察内容也可能包含不可信指令。网页或工具返回文本可以成为任务数据，但不能自动升级成系统规则。训练数据应包含这种边界，评价模型是否继续完成原始任务，而不是服从环境中的任意文字。

[WebArena](https://arxiv.org/abs/2307.13854)使用可控网页环境研究任务执行。它的重要启发是以环境状态检查是否完成任务，而不只评价最后一句“已完成”。在真实产品中，同样需要把动作产生的状态变化与自然语言汇报分开验证。

## 验收应该落在状态和行为上

对于前述加法环境，验收包括：未知工具被拒绝；参数缺失、额外字段、非数字与越界值有稳定错误；训练样本中工具观察的 loss mask 为零；第一步动作看不到未来结果；不同策略在相同题集和预算下比较。

再加入一次可控超时，并提供一次重试机会，检查策略是否无条件无限重试。若测试的是有状态任务，还要保存操作前后状态，确保“成功”不是因为环境里早就存在目标结果。

最后分别报告完整成功率与部分完成率，列出至少五条失败轨迹并标明失败阶段。一个能生成漂亮工具调用 JSON 的模型，只证明它掌握了部分输出格式；可靠 agent 还需要在新的环境状态中选对动作、正确处理观察并知道何时结束。
