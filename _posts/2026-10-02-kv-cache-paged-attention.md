## 缓存的是历史 K 和 V，不是整段生成结果

自回归解码每一步只增加一个新 token。对标准因果 Transformer，历史 token 的 K 和 V 在给定模型与前缀下可以复用，不必每一步重新计算。当前 token 的 Q 仍要与历史 K 交互，再以注意力权重组合历史 V。因此 KV Cache 减少重复计算，同时让显存占用随活跃上下文增长。

prefill 一次处理输入前缀并建立缓存，decode 则不断读取缓存、加入新条目。二者工作形态不同：长 prefill 有较大的矩阵计算，逐 token decode 的并行维度可能较小，并且频繁读取权重与历史缓存。缓存容量足够，不代表 decode 一定很快；读取这些字节也要时间。

## 从形状推导容量公式

令 L 为层数，Hkv 为 KV 头数，d 为每个头维度，s 为每个元素字节数，某请求当前缓存 T 个 token。在标准全注意力、各层布局一致且暂不考虑量化元数据时：

$$
M_{KV}=2LTH_{kv}ds.
$$

系数 2 来自 K 与 V。对于多个请求，应把各请求的实际缓存长度求和，而不是只乘最大长度。Hkv 必须使用 KV 头数；采用 GQA 或 MQA 时，它可能小于 query 头数，误用 query 头数会显著高估容量。滑动窗口、混合注意力层和特殊缓存布局还需要另行建模。

纸面例子：L=32、Hkv=8、d=128、BF16 的 s=2，每 token 占 131072 字节，即 128 KiB。4096 个 token 占 512 MiB；32 条同样长度的活跃序列合计 16 GiB。若 Hkv 变为 32，则同样缓存放大四倍。这个账本没有包含权重、临时激活、分配器与调度开销。

假设扣除其他用途后恰有 8 GiB 可用于 KV，按上述布局最多容纳 65536 个 token 槽位。这只是总槽位约束，不是可以接收 65536 条请求；每条请求至少要占自己的前缀和已生成部分，还要考虑增长空间与页面浪费。

## 连续分配为何容易浪费

若为每个请求预留最大输出长度，短请求提前结束时，许多预留位置从未使用。若按实际长度增长，连续内存区域又可能不易扩展，产生搬移或外部碎片。请求不断到达和结束，生命周期不同，使这个问题更明显。

PagedAttention 把逻辑上连续的 KV token 划成固定大小的块，让物理块可以分散存放，通过块表找到对应位置。它把内存管理问题与请求的连续逻辑位置分开，并为共享缓存块提供基础。[PagedAttention 原论文](https://arxiv.org/abs/2309.06180)解释了这一设计如何改善服务中的缓存利用率。

设每块可放 16 个 token，一个 33-token 请求需要三块，共 48 个槽位，最后一块浪费 15 个槽位。分页并没有让内存浪费绝对为零，它主要限制尾部内部碎片并避免为每个请求预留完整上限。块大小更小可减少尾部浪费，但会增大块表与管理开销，也影响 kernel 的访问组织。

vLLM 的 [分页注意力设计文档](https://docs.vllm.ai/en/latest/design/paged_attention/)展示了逻辑块与物理缓存布局。阅读时应注意实现和内核适用范围：学习块表思想，不等于所有模型、所有版本都使用同一种注意力内核。

## 分页、连续批处理与前缀共享是不同层次

分页解决缓存放在哪里；连续批处理决定每个解码轮次服务哪些请求。当一个请求完成，调度器可以释放资源并加入新的请求，不必等待最早形成的整批一起结束。缓存管理更灵活有利于这种调度，但单纯分页并不会自动制定公平的队列策略。

前缀缓存进一步利用完全相同的前缀。多个请求共享系统提示或文档前缀时，可以复用已计算的缓存块，降低重复 prefill 工作。共享块通常不能被任意覆盖；遇到分叉或修改，需要引用管理和必要的复制。匹配条件也不能只看可见文本：token 序列、模型版本、适配器及其他影响结果的身份需要一致。

[vLLM 自动前缀缓存文档](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)说明了其工作目标。前缀复用不会免除之后每个新 token 的 decode，也不会让两个语义相似但 token 不同的提示自动共用 K/V。缓存命中率提高是否改善端到端延迟，还取决于排队和输出长度。

## 从 token 生命周期检查缓存正确性

一个物理块通常经历空闲、分配、写入、读取、共享和释放等状态。请求逻辑长度增加时，最后一块未满就继续写入；跨过块边界才需要申请新块。请求完成时，应清理它的逻辑映射并递减引用，而不是假设所有关联块都归它独占。这个生命周期是内存安全与输出正确性的共同基础。

可构造两个长度接近块边界的请求来检查错误：一个刚好占满两块，另一个比它多一个 token。前者不应多申请空块，后者必须申请第三块。若结束后又复用这些物理块，新请求绝不能读取上一个请求留下的逻辑位置；物理存储复用不等于旧内容仍然有效。

前缀共享还要区分内容相同与身份兼容。两个请求的 token 序列相同，但使用不同适配器或不同权重版本，其缓存可能不同。把缓存键只设为字符串哈希会隐藏这种风险。缓存系统应把影响 K/V 结果的必要身份纳入匹配，并在版本切换时建立清晰的失效规则。

容量观察也应使用时间序列。平均占用较低，可能同时存在短暂的峰值导致抢占；反过来，占用长期较高也未必是问题，如果请求完成、资源回收和延迟都稳定。把缓存占用与每轮新分配块数、释放块数和等待队列一起记录，可以发现泄漏、回收延迟或准入过于激进等不同原因。单个百分比无法区分这些情形。

## 个人主机实验：做一个槽位账本

下例只用整数模拟容量，不安装 vLLM、不下载模型。长度是人为构造的请求状态，不是生产流量。

```python
import math

lengths = [33, 65, 17, 128]
block_tokens = 16
blocks = [math.ceil(n / block_tokens) for n in lengths]
reserved = sum(blocks) * block_tokens
used = sum(lengths)
waste = reserved - used
assert blocks == [3, 5, 2, 8]
assert waste == 45

bytes_per_token = 2 * 32 * 8 * 128 * 2
print("used MiB", used * bytes_per_token / 2**20)
print("reserved MiB", reserved * bytes_per_token / 2**20)
print("unused token slots", waste)

pool_blocks = 20
assert sum(blocks) <= pool_blocks
new_request_blocks = math.ceil(64 / block_tokens)
print("can admit now", sum(blocks) + new_request_blocks <= pool_blocks)
```

验收时应算出实际 token 总数为 243、保留槽位为 288。新请求需要四块，而当前只剩两块，因此不能直接接收。再让长度 65 的请求结束，释放五块，重新判断准入。将块大小改成 8 和 32，比较尾部浪费，但不要从这段 Python 运行时间比较 GPU 页表开销。

下一步可模拟两个请求共享前 32 个 token：只对完整共享块计算一次物理占用，并维护引用计数；一个请求结束时，只释放引用数归零的块。故意错误地释放仍被另一个请求使用的块，应触发断言。这验证共享缓存的生命周期，而非只是漂亮的容量公式。

## 容量不足时，调度策略会进入延迟指标

活跃请求增长可能触发排队、抢占、重计算或卸载，不同实现的选择不同。即使服务没有 OOM，频繁抢占也可能造成长尾延迟。应把可用块数、活跃与等待请求数、抢占频率、前缀命中率和请求长度分布一起观察，而不是只看缓存使用百分比。

还要预留输出增长风险：新请求的前缀可以装下，不代表它与现有请求继续生成时始终能装下。合理准入与逐轮调度应配合明确的长度限制和资源策略。最终验收既包括容量账本与实际分配吻合，也包括请求完成后资源能够回收、共享块不会误删，以及压力增加时服务仍满足定义好的延迟目标。
