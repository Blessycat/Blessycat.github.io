## 把“更快”改写成可比较的目标

训练性能应围绕固定工作量衡量。每秒 step 会受 batch、序列长度和梯度累积定义影响；每秒样本也可能掩盖文本长度差异。对于语言模型，一个有用指标是单位墙钟时间处理的有效训练 token 数，并明确是否排除 padding、被 mask 的 token，以及是否包含验证与检查点开销。

假设配置 A 每秒更新一次，每次 32768 个有效 token；配置 B 每秒更新两次，每次 8192 个有效 token。B 的 step/s 翻倍，token/s 却只有 A 的一半。若 B 同时改变了数据顺序或目标损失分母，即便 token/s 更高也不是单纯的系统优化。

比较实验必须固定模型、数据和精度等关键条件，并记录设备、依赖、批量、长度分布与编译设置。预热阶段应单列，因为首次运行可能包含初始化、内核选择、缓存建立或编译。稳态吞吐和启动成本都重要，但不能把两者混在一个模糊平均数中。

## CPU 计时可能只测到了提交动作

GPU 通常异步执行，主机调用返回并不表示设备工作已经完成。直接在 GPU 调用前后读取墙钟，可能只测到任务入队。测单段设备工作可使用设备事件；测完整窗口可在边界进行同步，而不是在每个算子后同步。后者会破坏原本存在的重叠。

CPU 实验也有噪声：线程池、后台进程、缓存和动态频率都会影响结果。不要仅跑一次取最小值，然后与另一个配置的平均值比较。[PyTorch Benchmark 教程](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)提供了关于预热、线程数和同步的测量思路。

多卡场景中，一次更新结束的时间由最慢的参与者决定。只看 rank 0 的本地算子表可能忽略其他 rank 的数据等待或长序列。应比较每个 rank 的步骤分布，并在时间线中查找它们何时开始等待彼此。分布式计时还要警惕不同主机时钟，优先用各进程局部持续时间配合统一事件关联。

## 算子累计时间不等于端到端时间

假设纸面时间线里，计算持续 80 毫秒，通信总计 50 毫秒，其中 40 毫秒与计算重叠，末尾另有 10 毫秒暴露通信。再加 10 毫秒无法重叠的数据等待，步骤时间约为 100 毫秒，而不是 140 毫秒。简单把算子表里的耗时相加，既可能重复计算父子事件，也可能重复计算并发事件。

应沿着依赖关系找关键路径：下一阶段究竟在等待数据、某个 kernel、最后一个梯度桶，还是主机调度？通信算子持续很久，有时不是网络慢，而是某个 rank 更晚进入了集合操作。等待包含了上游延迟，不能直接把责任归给通信库。

若端到端时间中只有 20% 是准备优化的部分，即使它被无限加速，整体加速比也最多为：

$$
S_{max}=\frac{1}{1-0.2}=1.25.
$$

这条上界可以防止花大量时间优化无关紧要的小算子。反过来，一个占比不大的同步点可能截断并发，使周围任务全部串行；它的删除效果又不能只从本身耗时估算。因此累计表用于筛选，时间线用于解释。

## 一次 profiling 应服务于一个假设

例如观察到 GPU 间歇空闲，提出“数据加载供应不足”的假设。先保持训练工作不变，仅用内存中的固定 batch 运行，比较空闲段是否缩短；若缩短，再分别检查读取、解码、拼接、拷贝。这个对照实验比同时增加 worker、启用缓存、改 batch 和开启编译更容易归因。

常见时间线形态也各有可能原因。大量短 kernel 之间主机有空隙，可能受启动开销或 Python 调度影响；长 GEMM 连续占满设备，可能受计算约束；反向结束后 NCCL 长尾，可能是同步暴露；周期性的长停顿，则要关联检查点、垃圾回收或数据文件切换。

[PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html)适合关联框架算子、用户标记与设备活动；[NVIDIA Nsight Systems 用户指南](https://docs.nvidia.com/nsight-systems/UserGuide/index.html)适合进一步检查主机线程、CUDA 提交和跨流关系。工具的分工并不意味着一次要全部启用，先收集少量代表性步骤，避免巨大 trace 难以阅读。

启用堆栈、形状和内存追踪会增加开销，因此 profiler 下的吞吐不能直接当作最终性能成绩。定位后关闭分析功能，用相同工作量重新计时；否则优化结果可能只是对 profiler 开销的敏感度变化。

## 用重复实验区分改善和测量噪声

假设基线二十次更新的中位数为一百毫秒，改动后为九十八毫秒，但同一配置重复运行的中位数在九十六到一百零四毫秒之间波动。仅凭这一对数字，不足以声称改动稳定改善了性能。更好的方法是多轮交替运行两个配置，保持温度、后台负载和输入分布尽量一致，查看差异是否持续出现。

每轮测量应保存原始步骤时间，而不只是最后的均值。若偶发检查点使一个步骤明显变慢，应该根据预先约定的口径决定计入还是单列，不能看见异常值后才临时删除。面向稳态算子优化可以单列周期性任务，面向整场训练预算则必须把它们重新纳入墙钟成本。

吞吐统计还有一个常见错误：先算每一步的瞬时速度，再简单平均。若两个步骤完成同样数量的 token，却分别耗时一秒和三秒，平均瞬时速度会高估整段速度。正确的窗口吞吐应使用总有效 token 数除以总时间；对于不等长步骤，这个区别更加重要。

同样，先将所有 rank 的吞吐相加之前，要确认它们统计的是不同数据。张量并行和流水线阶段处理的是同一份逻辑样本的不同部分，重复相加会虚增工作量。训练性能统计最好从数据并行副本的全局有效样本或 token 计数出发，再对齐统一更新窗口。

## 个人主机实验：从两个阶段的计时开始

下面用标准库构造“准备数据”和“消费数据”两个阶段，记录毫秒分布。它是 CPU 测量练习，结果随主机变化，不代表 GPU 训练，也不预设哪个阶段一定更慢。

```python
from time import perf_counter
from statistics import median

def prepare(size):
    return [float(i % 97) for i in range(size)]

def consume(values):
    return sum(v * v for v in values)

for _ in range(3):
    consume(prepare(50_000))

prepare_ms, consume_ms, total_ms = [], [], []
for _ in range(20):
    start = perf_counter()
    values = prepare(50_000)
    split = perf_counter()
    result = consume(values)
    end = perf_counter()
    prepare_ms.append((split - start) * 1000)
    consume_ms.append((end - split) * 1000)
    total_ms.append((end - start) * 1000)
    assert result > 0
print("median ms", median(prepare_ms), median(consume_ms), median(total_ms))
```

验收不是跑出某个固定速度，而是能保留原始样本，解释测量边界，并构造对照：预先准备一份列表，只测消费阶段；然后把列表长度翻倍，观察时间变化是否稳定。两个阶段各自的中位数相加不一定等于总时间中位数，因为它们的排序可能不同，应从逐次样本理解统计口径。

已有 PyTorch 环境时，可把小模型运行包装进 `profile`，用 `record_function` 标记数据准备、前向、反向和更新，导出一小段 trace。此时仍应先确认输出和损失一致，再解释性能变化。若改变线程数，必须把线程数写进结果，而不是把它藏在环境里。

## 为一次优化留下可复查的证据

一条完整结论应回答：固定了什么、改变了什么、测了多少次、使用哪个统计量、改善了哪个等待区间，以及是否保持训练正确性。可以报告“在此环境与长度分布下，关闭 profiler 后的中位有效 token/s 提升”，同时列出尾部延迟与显存变化；不要从一个微基准推断所有模型都能提速。

当瓶颈转移，下一步优化对象也会变化。数据供应足够快之后，继续增加 worker 可能只提高内存占用；通信被覆盖后，再提升网络峰值未必降低步骤时间。性能工程的闭环是提出假设、做单变量对照、验证关键路径改变，再保留可复算的数据。
