## 并行维度不同，切开的对象也不同

数据并行把不同样本交给模型副本，张量并行把同一层的张量计算切开，流水线并行把模型的不同层放到不同阶段，专家并行则按 MoE 专家分配参数和 token。把这些缩写写成配置矩阵之前，应该能指出每个进程拥有什么，以及下一步要向谁索取数据。

例如“八张 GPU”只规定总资源，不能决定并行策略。一个模型可能用八路数据并行，也可能用两路张量并行乘四路数据并行。两者每个进程的参数量、处理的独立样本数和通信频率都不同。后者的有效 batch 应按数据并行副本数计算，不能把张量并行参与者再次算成独立数据副本。

## 张量并行：切输出列与切输入行

令 X 的形状为 m×d，权重 W 的形状为 d×h。沿 W 的输出维切成 W₁ 和 W₂，两张设备计算 XW₁ 与 XW₂，结果分别是输出特征的不同列。如果下一层可以直接消费这种布局，就无需马上把完整输出聚合。[Megatron-LM 原论文](https://arxiv.org/abs/1909.08053)展示了如何在 Transformer 内组织互补的矩阵分片。

另一种切法是把输入特征和权重输入维一起分片。令 X=[X₁,X₂]，W 由 W₁、W₂ 沿行堆叠，则：

$$
XW=X_1W_1+X_2W_2.
$$

各 rank 获得的是完整输出形状的部分和，因此需要规约。按列切分后的逐元素非线性，可以在本地完成；紧接着的按行切分层再汇总部分和，就能减少中间聚合。这种推导比记住“每层有几次 AllReduce”更耐用，因为序列并行、融合和具体实现都会改变通信安排。

纸面例子：有 4096 个 token，隐藏维 4096，BF16 激活完整大小约为 33.55 MB。即使权重已经切小，频繁交换这一级别的激活仍可能昂贵。TP 常希望使用低延迟、高带宽互联，但“必须在单节点”不是数学限制；是否跨节点取决于实际网络与计算通信比例。

## 流水线并行：切层以后还要让各阶段有活干

把四段连续层放在四个阶段，只送一个微批时，后面阶段等待前面完成，许多设备空闲。把一个训练 batch 切成 M 个微批后，第一阶段可以处理下一微批，同时第二阶段处理上一微批。GPipe 以这种方式组织训练，并讨论了微批和重计算的组合。[GPipe 原论文](https://arxiv.org/abs/1811.06965)是理解基本调度的直接资料。

对 S 个速度相同的阶段、M 个微批，忽略通信、假设前后向阶段成本相同，在简单填充再排空的训练日程下，理想利用率近似为：

$$
U\approx\frac{M}{M+S-1}.
$$

S=4、M=8 时约为 72.7%；M=32 时约为 91.4%。这些只是日程模型结果，不代表某框架或集群的实测效率。增加微批数可能降低气泡比例，但固定总 batch 下每个微批更小，又可能降低矩阵乘法效率并增加调度开销。

阶段平衡比平均层数更重要。嵌入、输出投影、不同序列长度和不同层结构会让等层数切分仍然不等时。若四个阶段分别耗时 2、2、5、2 毫秒，稳态节拍受 5 毫秒阶段限制。把瓶颈阶段的工作迁移出去，比继续增加微批更有针对性。

常见的 1F1B 日程在稳定区间交替执行前向与反向，有助于控制保留激活的数量。它不意味着每个微批都立即更新权重；若一个有效 batch 内不同微批使用不一致的参数版本，训练语义会改变。读调度实现时要同时追踪激活生命周期和参数版本。

## 专家并行：稀疏计算并不等于没有通信

MoE 中路由器为 token 选择少数专家，EP 把专家参数放在不同设备。token 先按目的专家重排并发送，专家计算后再将结果送回原位置，按门控权重合并。因此路由分发、专家计算和回传共同构成关键路径。Switch Transformer 使用简化的稀疏路由，并讨论了容量与负载均衡问题。[Switch Transformer 原论文](https://arxiv.org/abs/2101.03961)说明了这些设计动机。

假设 1024 个 token 路由到 8 个专家，每个 token 只选择一个专家，理想平均为 128。如果某个专家收到 300，其余专家分摊剩余 724，那么最繁忙专家的负载约为平均值的 2.34 倍。总 token 数没变，但步骤可能被该专家拖慢。

若容量因子为 1.25，按简单公式每个专家容量为 160；热门专家超出的 140 个 token 如何处理，必须由算法明确规定。丢弃、改路由与无丢弃执行会带来不同的质量、显存和延迟影响。不能只写“开启均衡”就忽略极端路由分布，也不能假设总参数很大就意味着每个 token 的计算同样大。

## 用一个进程坐标表理解组合并行

设有十六个 rank，采用两路张量并行、两路流水线并行和四路数据并行。可以给每个进程分配三个坐标：数据副本编号、流水线阶段编号、张量分片编号。保持前两个坐标相同，改变最后一个坐标，就得到一组张量并行伙伴；保持阶段与分片位置相同，改变数据副本编号，则得到需要同步对应梯度的数据并行组。

这十六个进程共同提供四份独立模型副本，每份副本由四个进程合作执行。若每个副本的微批为两条样本，累积八次，则有效 batch 为六十四条，而不是二百五十六条。流水线中的阶段虽然都看到了这些样本的某种激活，它们没有创造新的独立样本。

接着给这张坐标表标注物理机器。频繁交换激活的张量伙伴适合优先考虑快链路，流水线相邻阶段则需要传输边界激活。数据并行通信也会竞争链路，因此不能只为某一种通信安排理想位置。实际放置是综合约束问题，必须看同一时间有哪些传输并发发生。

在小模型上验证组合布局时，可以先禁用随机性，把完整模型的输出与分片重组输出进行比较，再比较参数梯度。前向一致但梯度不一致，常见原因是反向缺少规约、重复规约或分母计算错误。只有一次更新正确后，再测试多个微批和多个更新，才能发现流水线缓冲复用或版本推进的问题。该过程关注算法等价性，不要求在普通主机上复现真实拓扑速度。

## 个人主机实验：验证拆分等价与负载偏斜

不安装 GPU 依赖，先用列表验证按输入维切分的矩阵乘法。这里 X 只有一行，已经足以检查部分和为什么需要相加。

```python
x = [1, 2, 3, 4]
w = [[1, 0], [0, 1], [1, 1], [2, 1]]
def project(xs, rows):
    return [sum(a * row[j] for a, row in zip(xs, rows))
            for j in range(2)]

whole = project(x, w)
left = project(x[:2], w[:2])
right = project(x[2:], w[2:])
assert whole == [a+b for a, b in zip(left, right)]

loads = [300, 104, 104, 104, 103, 103, 103, 103]
assert sum(loads) == 1024
print("load ratio", max(loads) / (sum(loads) / len(loads)))
for microbatches in [1, 8, 32]:
    print(microbatches, microbatches / (microbatches + 4 - 1))
```

验收时，能够把第一段改为输出列切分，并说明为何这次应拼接而非相加；能够把热门专家负载翻倍，并预测容量溢出数量；能够解释 M=1 的低利用率来自依赖而非“GPU 不够快”。这些实验只验证计算结构与离散模型，不模拟真实设备吞吐。

进入真实部署前，画一张进程组表，列出每个 rank 的 DP、TP、PP 和专家归属，以及各组使用的链路。专家并行并不总是一个能直接相乘的额外独立维度，它可能与数据并行组共享资源。当前框架的分组与组合约束应查阅 [Megatron Bridge 并行指南](https://docs.nvidia.com/nemo/megatron-bridge/latest/parallelisms.html)，不要凭缩写乘积配置通信组。

最终要比较的是固定训练目标下的吞吐、峰值显存和更新正确性。先通过小规模等价性检查，再看时间线上的规约、阶段等待与路由偏斜，才能知道增加哪一种并行维度真正有帮助。
