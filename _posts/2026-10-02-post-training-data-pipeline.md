先修要求：JSONL、哈希和聊天模板。示例只使用 Python 标准库；真实分词阶段需要事先准备 tokenizer。本篇不包含下载数据或运行大模型的步骤。

数据处理不是训练前的杂务，它决定了模型实际优化什么。一个有十万行的文件，可能只有两万条独立问题；随机拆分后，测试题的改写版本可能已经出现在训练集；打包提高了 token 利用率，也可能悄悄改变样本间的可见关系。本篇要建立的是一条能解释每条记录去向的数据流水线。

## 先定义记录，不要先定义清洗正则

一条最小训练记录应包含稳定 ID、来源组、消息列表以及必要的处理元数据。来源组可以是同一原始文档、同一会话或同一合成任务的派生族。它不是展示字段，而是之后防泄漏拆分的重要依据。

校验先回答结构问题：消息是否为列表，角色是否合法，内容是否为空，是否包含期望的助手回答。再回答任务问题：答案是否满足格式要求，是否与问题矛盾，是否存在明显截断。结构合法不能证明答案正确；反过来，人工觉得“有用”的样本也可能无法通过训练器接口。

清洗规则应限定作用范围。删除自然语言两端无意义空白通常容易解释，但代码缩进、表格分隔符或精确字符串任务中的空格可能是答案的一部分。与其写一个越来越激进的通用清洗器，不如为任务类型定义少量可审计规则，并保留原始记录与拒绝原因。

## 去重解决的是权重与泄漏

完全重复可以通过规范化后的文本摘要检测，近重复则需要额外方法，例如基于字符片段的相似度或人工抽查。完全相同的问题出现 100 次，会在常见均匀采样策略中获得约 100 倍采样机会，因此重复同时改变了训练权重。

研究发现，训练语料去重与记忆、数据重叠等问题有关，但某篇论文的结果不能直接保证任意数据集去重后都会提高指标。应该在自己的目标任务上检验去重策略。[Deduplicating Training Data Makes Language Models Better](https://arxiv.org/abs/2107.06499)

教学上可从两级标识开始：内容摘要发现完全重复，来源组 ID 聚合改写与派生样本。若同一重复簇来自不同组，应在拆分前合并其关联，或按明确规则统一归属，不能各删一半后宣称没有交叉。对近重复的检查也应跨训练与评测边界进行。

## 先按独立来源拆分，再做派生处理

假设原始数据有 100 篇文档，每篇生成 20 道问答，共 2000 条。按行随机拆分，很容易让同一文档的一部分进入训练、一部分进入测试。此时测试更接近“是否记住这篇文档”，而未必是“是否能处理新文档”。

若目标是泛化到新文档，就应以文档为拆分单元。若目标是泛化到未来时间段，按时间拆分更合适；若部署环境会见到相同文档的新提问，则可以设计另一种独立评测。拆分策略来自问题定义，不存在对所有任务都正确的随机比例。

下面用稳定哈希给组分配集合，适用于已有可靠 `group_id` 的教学记录。它让同一组始终去同一集合，但不能保证小数据集恰好得到 90%、5%、5% 的数量。

```python
import hashlib

def split_for_group(group_id: str) -> str:
    payload = ("split-v1:" + group_id).encode("utf-8")
    bucket = int(hashlib.sha256(payload).hexdigest(), 16) % 100
    if bucket < 90:
        return "train"
    if bucket < 95:
        return "validation"
    return "test"

rows = [
    {"id": "a1", "group_id": "doc-a"},
    {"id": "a2", "group_id": "doc-a"},
    {"id": "b1", "group_id": "doc-b"},
]
for row in rows:
    row["split"] = split_for_group(row["group_id"])
assert rows[0]["split"] == rows[1]["split"]
```

不要用 Python 内置 `hash()` 充当持久拆分规则，因为它可能随进程设置改变。对分布很不均匀的数据，还需要在组级别检查类别和长度分布。HF Datasets 的 map、filter、shuffle 和拆分操作可以承担处理工作，但流水线语义仍由使用者负责。[Datasets Process](https://huggingface.co/docs/datasets/process)

## 分词后再统计真实训练预算

记录条数适合描述样本数量，token 数更接近计算工作量，有效监督 token 数则更接近优化目标。三者应该分别统计。1000 条长上下文、短回答样本，可能带来大量计算，却只有少量监督信号。

建议保存模板前后的长度分位数、截断比例、每个集合的总输入 token 数和有效目标 token 数。假设一条样本总长 400，其中助手回答只有 40 token，那么输入预算利用率与监督密度是两个不同量。不能把处理了 40 万输入 token 写成训练了 40 万回答 token。

随机增强、改写、切块都应在拆分策略确定后沿来源组继承归属。尤其不能先把一篇长文拆成重叠窗口，再对窗口随机拆分；相邻窗口共享大量文本，会产生非常隐蔽的评测泄漏。

## packing 不只是把短句拼长

假设有 100 条长度均为 100 的样本，若每条固定补齐到 512，需要处理 51,200 个位置，其中有效输入只有 10,000，利用率约 19.5%。把每五条放入一个 512 长度块，忽略额外边界开销，利用率约为 97.7%。这些是固定补齐策略下的算术对比；动态 padding、长度分桶也能减少浪费，不能把它当作所有训练器的实测提升。

拼接后必须回答：后一条样本能否看到前一条？仅插入 EOS 并不会阻断注意力。若希望样本独立，需要分段因果掩码或受支持的序列边界机制，并正确处理位置编号。边界后第一个 token 的预测目标也要按设计处理，避免把“从前一条样本预测下一条开头”意外纳入损失。

也可以有意使用连续文本训练目标，让后段读取前段，但那是另一种数据语义，应明确记录。某个框架声称支持 packing，不代表它的所有策略都使用同样的隔离方式；需要核对所选版本、策略与注意力后端。[TRL SFT Trainer packing](https://huggingface.co/docs/trl/sft_trainer)

## 数据报告要能解释分布变化

每条过滤规则都应同时报告数量和比例，并按来源或任务检查差异。例如总共只删除了 5% 样本，看起来很温和，但若删除的全是长问题，就可能大幅改变目标能力。拒绝日志可以保存记录 ID 与原因，不必在公开报告里重复原始文本。

数据版本也不应只靠最终文件的修改时间命名。将输入清单、处理脚本版本、参数和输出摘要一起保存，才能区分“同一算法换了输入”和“同一输入换了算法”。没有这些信息时，后续模型差异很难归因。

## 主机实验与验收

用标准库构造 30 个虚构来源组，每组两条改写问题，再人为加入五条完全重复、两条空答案和三条超长记录。为每一步保存输入条数、输出条数与拒绝原因。预期能追溯到哪些记录被删除，但本篇没有声称运行过这套数据。

首先断言 train、validation、test 的组 ID 两两不交叉；随后跨集合比较规范化内容摘要；最后抽取打包块，打印每个 token 的样本归属、位置编号、监督标记和可见区间。若打算用独立样本 packing，修改前一个样本内容后，后一个样本的输出不应受它影响，这可作为之后模型侧的行为验收。

最终交付应包含版本化处理脚本、数据清单与小型审计报告。有效验收不是“没有空行”，而是重复率、截断率和集合边界都有定义，并且能够从任意训练样本回溯到来源与处理步骤。数据数量增加之前，先让数据含义稳定下来。
