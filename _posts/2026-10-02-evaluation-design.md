训练 loss 下降说明模型更擅长拟合所定义的训练目标，但用户关心的通常是另一件事：在新的输入上，答案是否更正确、更符合格式，且没有损害原来的能力？评测应先把这个问题写清楚，再选择指标与工具。否则数字越多，反而越难判断是否进步。

## 先定义测量对象，再选指标

结构化抽取可以把“格式可解析”和“字段内容正确”分开；问答可以区分答案正确性、证据支持与拒答行为；代码任务可能需要隔离环境中的可执行测试。一个任务常有多个维度，平均成单个分数之前，应明确每项的作用和权重。HELM 的研究框架强调语言模型评估应覆盖多种场景与指标，而不是只有一张总排行榜。[Holistic Evaluation of Language Models](https://arxiv.org/abs/2211.09110)

例如模型 A 的 JSON 解析成功率为 98%，字段完全正确率为 70%；模型 B 分别为 93% 与 76%。B 不是无条件更好：如果下游无法处理非法 JSON，格式退化可能抵消内容收益。评测报告至少应保留这两个原始指标，让选择对应真实约束。

还应固定生成条件，包括模板、系统提示、最大输出长度、采样方式和停止 token。微调模型用 512 个输出 token，底座只用 64 个，比较结果混合了训练变化与预算变化。工具版本和任务配置也需要冻结；评测框架只能执行协议，不能替代协议设计。[EleutherAI lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)

## 测试集是未参与选择的证据

训练集用于更新参数，验证集用于选择超参数和检查点，测试集用于对最终选择做一次独立评估。若反复看测试集并据此改 prompt、筛数据或换学习率，测试集已经参与开发，即使没有进入梯度计算，也会产生选择偏差。

泄漏不仅是逐字重复。来自同一文档的改写问答、同一模板的参数变体、答案解释中出现测试题，都可能形成更弱但仍重要的关联。应按目标泛化单位拆分，并做跨集合的完全重复与近重复检查。对公共基准，还要承认无法总是确认底座预训练是否见过相关内容。

实用做法是维护两组评测：一组稳定的小型开发集，用于频繁排错；另一组冻结测试集，在方案确定后使用。若测试结论导致新的开发，应新增后续独立评估或清楚标记原测试集已被用于迭代，而不是继续称其为完全未见。

## 2.5 个百分点可能只是样本波动

假设 200 道独立二元题中答对 120 道，正确率为 60%。用简单正态近似，其标准误差约为：

$$
\operatorname{SE}\approx\sqrt{\frac{0.6(1-0.6)}{200}}\approx0.0346.
$$

粗略 95% 区间约为 53.2% 到 66.8%。它适合帮助理解抽样波动，不是所有比例场景下都理想的区间方法；样本少或接近 0、1 时应使用更合适的构造。更重要的是，比较模型时应利用同一题目上的成对结果，而不是把两个独立区间简单相减。

若底座与微调模型面对同样的题，定义每题差值为“微调是否正确减去底座是否正确”。两者都对或都错时差值为零；一胜一负时为正负一。对这些差值做成对 bootstrap，能保留题目难度的对应关系。

```python
import random
from statistics import mean

# 完全人工构造的教学数据：(底座结果, 微调结果)。
pairs = ([(1, 1)] * 105 + [(1, 0)] * 15
         + [(0, 1)] * 20 + [(0, 0)] * 60)
diff = [candidate - base for base, candidate in pairs]
rng = random.Random(42)
replicates = sorted(
    mean(rng.choices(diff, k=len(diff))) for _ in range(2000)
)
lo = replicates[int(0.025 * (len(replicates) - 1))]
hi = replicates[int(0.975 * (len(replicates) - 1))]
print("difference:", mean(diff), "percentile interval:", (lo, hi))
```

这组教学计数的点估计差值为 0.025。区间需要运行代码计算，不能把某个预期区间冒充真实测量。若多个问题来自同一文档，应按文档组重采样，而不是把高度相关的问题当成独立样本。SciPy 的 bootstrap 接口也支持成对重采样，但仍需要使用者选择正确的统计单元。[SciPy bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)

## 模型裁判解决开放式答案，却引入新的误差

开放式总结或建议不容易写成精确匹配，可以让另一个模型依据评分标准判断。但裁判本身存在位置、长度、措辞和偏好等偏差，不能把它的输出当作无误的人工真值。MT-Bench 与 Chatbot Arena 相关论文专门研究了模型裁判的能力与局限。[Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)

一个实用协议应明确：裁判可见题目、参考信息和候选答案，分别评什么维度，允许哪些分数，什么时候必须判为无法判断。成对比较时随机交换 A/B 位置，隐藏模型身份；对一部分样本重复交换并检查判定是否稳定。不要让“写得长”默认等于“答得好”。

先抽取一小批样本做人工校准，包含明显正确、明显错误、部分正确、格式错误和具有迷惑性的流畅错误答案。若裁判连这些边界都分不清，扩到几千条只会更精确地测量一个有偏指标。还要保存裁判版本、完整提示和原始判定，以便复查。

被评答案可能包含“忽略上面的规则”等内容，裁判提示应把它明确标为待评估数据。对高风险或关键决策任务，自动评分需要人工复核。这里的目标是防止评测协议被答案内容改变，而不是假设所有长文本都不可评估。

## 看平均值，也看失败结构

总分不变可能掩盖显著变化：简单题提高、复杂题下降，短输入提高、长输入下降，格式更稳但事实更差。预先定义少量有意义的切片，如输入长度、任务类别和难度，再报告样本数与分数。切片过多也会产生偶然“显著”结果，因此探索性发现要与预先规定的主指标分开。

模型随机种子带来的训练波动与测试题抽样带来的统计波动也不同。一次训练的 bootstrap 区间不能代表换种子重训后的变动。资源允许时，对候选配方运行多个训练种子，并保留每次在同一评测集上的结果。

## 主机实验与验收

先运行人工成对结果的统计脚本，再把每个样本复制十次。如果错误地把副本当独立题目，区间会变窄，却没有新增真实信息。这个小实验能直观说明独立样本数为什么比文件行数重要。

为一个自拟格式转换任务写 20 条开发题和一组独立测试题，先用确定性规则评分，不接模型裁判。验收是同一输出重复评分完全一致、非法格式被正确识别、底座与候选使用同一输入协议，且每个失败能定位到原始输出。

只有当指标无法覆盖重要质量维度时，再加入人工或模型裁判。最终报告应明确样本来源、生成条件、主指标、成对差异与局限；若证据不足，就写“未确认改进”。这比把单次略高的数字包装成稳定提升，更有助于决定下一次训练该改什么。
